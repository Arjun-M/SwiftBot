The Telegram framework that grows with your bot.

Most Python Telegram SDKs give you one programming style: imperative handlers and a grab-bag of loose utilities. SwiftBot is built around composable abstractions instead — declarative pipelines with dependency injection, typed command specs, an outbound transformer layer, middleware bundles with error boundaries, typed wizards, state-carrying dialogues, scoped middleware chains, outbound throttling, and a fluent reply builder. Everything is idiomatic Python, all optional, and every piece stacks on the small async core.

Quickstart — the whole v1.5 experience in one file

from swiftbot import SwiftBot, BotCommands, Composer, F, plugins
from swiftbot.commands import CommandsMiddleware

class Cmd(BotCommands):
    start = "/start"                     # declarative command spec
    name = "/name <first> <last>"        # parsed args, typed
    help_ = "/help"                      # auto-generated from the class

bot = SwiftBot(token="TOKEN:HERE")
bot.use(CommandsMiddleware(Cmd))         # /help appears for free

# Anti-spam + per-user rate limit, as first-party middleware bundles
from swiftbot.plugins import spam_deflector, session_limiter
bot.use(spam_deflector(threshold=15))
bot.use(session_limiter(min_interval=0.5))

# F filter algebra — plain-English composition on any update
@bot.on(F.text & F.private & ~F.forwarded)
async def echo(ctx):
    await ctx.reply(f"You said: {ctx.text}")

# A scripted test — no network, no Telegram
from swiftbot.testing import TestClient
async def test_echo():
    async with TestClient(bot) as tc:
        await tc.send_update({"update_id": 1,
            "message": {"message_id": 1, "date": 0,
                        "chat": {"id": 42, "type": "private"},
                        "from": {"id": 7, "is_bot": False, "first_name": "U"},
                        "text": "Hello world"}})
        assert tc.outgoing[0]["params"]["text"] == "You said: Hello world"

What Drove v1.5

Every feature in v1.5 came out of a single question: what do bot developers complain about in Python, and what do developers on other platforms get for free? Surveying the whole ecosystem — including what Rust, TypeScript, Go and Kotlin bot SDKs do — the same five gaps kept surfacing in every Python package. SwiftBot closed all five, and made them native Python.

Gap in every Python SDKWhat mature platforms get rightSwiftBot's answer
Handlers receive only the context — no way to request dependencies without globals. Handler trees where functions declare their parameters and the framework injects them; typed command parsing with auto-generated help. Pipeline + DI, BotCommands
No hook on outgoing API calls — everything intercepts inbound only. Outbound transformer stacks (auto typing, dry-run, recording); composable middleware bundles with error boundaries; pre-handler dispatch by update kind. TransformerConfig, Composer, route()
Middlewares are either global or per-handler, with no grouping and no error isolation. Scoped middleware chains and failure isolation — one broken plugin can never crash a sibling. Middleware layer + plugins registry
Keyboard markup is built by hand, line after line of dicts. Fluent, chained builders with type-safe markup. Builder-style APIs (Pipeline.deps().handle(), wizard decorators)

Five years after the first python-telegram-bot release, no Python Telegram SDK offers a dependency-injection handler tree, an outbound transformer layer, or an error-boundary composer — the three capabilities developers reach for most when a bot starts getting serious. SwiftBot changes that.

Pipelines + Dependency Injection

In every Python framework, handlers receive exactly one object: the context. Need a database? A config? An LLM client? You reach for globals or closures. SwiftBot's Pipeline solves this the way declarative trees do: handler functions declare the dependencies they need by parameter name, and the framework injects them — nothing global, nothing implicit. 

from swiftbot.pipeline import Pipeline
from swiftbot.filters import F

async def stats(ctx, db, redis):          # ctx, db and redis injected by name
    count = await db.count_users()
    await ctx.reply(f"{count} users · {await redis.ping()}")

pipe = Pipeline()
pipe.deps(db=my_postgres).deps(redis=my_redis)
pipe.handle(F.command("stats"), stats)
pipe.handle(F.text, fallback_handler)

bot.pipeline(pipe)                        # mount — the pipeline is one middleware stage

Branches are evaluated in registration order with first-match-wins semantics (toggle via Pipeline(first=False) to run all matches). If a handler declares a dependency that was never registered, the pipeline raises PipelineDependencyMissing immediately — failures are loud, never silent. Framework parameters ctx, bot and match (the last regex match) are always available and never taken from the registry.

Declarative BotCommands

Declaring commands once as a spec — with arguments parsed automatically and a correct /help generated from descriptions — is a capability most platforms treat as table stakes. SwiftBot's BotCommands brings it to Python — no decorators needed, and names that collide with built-ins (Cmd.name, Cmd.help) are handled safely. 

from swiftbot.commands import BotCommands, CommandsMiddleware

class Cmd(BotCommands):
    start = "/start"
    name = "/name <first> <last>"
    age = "/age <years:number>"          # type coercions: int, float, bool
    help_ = "/help | /h"                 # aliases

bot.use(CommandsMiddleware(Cmd))

# The spec doubles as a filter — register handlers against commands directly:
@bot.on(Cmd.name)                        # Cmd.name is a callable filter + parsed spec
async def greet(ctx):
    parsed = Cmd.parse(ctx.text)          # ParsedCommand(name='name', args=['Arjun','M'])
    await ctx.reply(f"Hello, {parsed.args[0]}!")

CommandsMiddleware intercepts /help and renders a table of every declared command, its usage line and arguments — the same contract a typed CLI gives you, in a chat window.

Outbound Transformers

Middleware intercepts incoming updates. Who intercepts outgoing API calls? Nobody in the Python ecosystem — which is why SwiftBot added an outbound transformer stack. bot.api.config.use() wraps every call through TelegramAPI._request with a stack of transformers (method, payload) → payload. 

from swiftbot.transformer import (
    auto_typing, call_logger, idempotency_guard, Recorder, record
)

# Send the typing indicator while an upload runs:
bot.api.config.use(auto_typing(interval=5.0))

# Make every sendMessage idempotent for 30 seconds:
bot.api.config.use(idempotency_guard())

# Log every outbound call:
bot.api.config.use(call_logger(lambda m, p: print(m, list(p))))

# Patch defaults into every call (e.g. force MarkdownV2):
from swiftbot.transformer import payload_patch
bot.api.config.use(payload_patch(parse_mode="MarkdownV2"))

The Recorder — test against scripted Telegram

from swiftbot.transformer import Recorder

rec = Recorder()
rec.script("getMe", result={"id": 1, "is_bot": True, "first_name": "Bot"})
rec.script("sendMessage", result={"message_id": 42, "text": "ok"})

bot.api.config.use(rec)

result = await bot.api.send_message(1, text="hi")   # no network — returns {"message_id":42}
assert rec.calls[0]["method"] == "sendMessage"      # every call is recorded

Combined with swiftbot.testing (v1.4's FakePool + TestClient), SwiftBot now offers the strongest network-free testing story of any Python Telegram framework.

Composer — Middleware Bundles with Error Boundaries

Middleware scattered across bot.use() calls is hard to reason about, and a single broken plugin can crash the whole bot. SwiftBot's Composer lets you package middleware into modules and — most importantly — attach an error boundary to a bundle so that one misbehaving plugin can never crash the rest. 

from swiftbot import Composer

bundle = Composer()

async def metrics(ctx, next_handler):
    t0 = time.monotonic()
    await next_handler()
    record_metric(time.monotonic() - t0)

async def on_error(ctx, exc):            # this boundary isolates the bundle
    await alert_channel.send(f"Plugin error: {exc!r}")

bundle.use(metrics, plugins.SessionLimiter())
bundle.catch(on_error)

bot.use(bundle)                          # an exception inside this bundle never reaches others

Composers nest freely — a bundle can contain other bundles, each with its own boundary. Without a boundary, exceptions propagate exactly once, up the chain, so they are always visible to your central exception handler rather than being silently swallowed.

Dispatch Routing

Sometimes a middleware chain should run per update kind, before any handler is evaluated — for example an admin gate that must fire on every message type. SwiftBot's bot.route() picks a handler stage per update kind (or any boolean predicate on the raw update), ideal for separating business-logic modules, admin gates, and per-chat pipelines. 

async def admin_only(ctx, next_handler):
    if ctx.user.id not in ADMIN_IDS:
        return
    await next_handler()

bot.route({
    "message": Composer(admin_only),
    "callback_query": Composer(plugins.idempotency()),
    "poll": Composer(CheckpointRecorder()),
})

Typed Wizards

Most Python FSMs give you string states and a free-form data dict. SwiftBot's Wizard keeps steps as plain async functions while collected answers accumulate into a structured result object — no stringly-typed state machine, no magic dicts. The wizard is storage-agnostic (Memory, JSON file, or Redis). 

survey = bot.wizard("survey", storage=None)     # falls back to the bot's storage

@survey.step("ask_name")
async def ask_name(ctx):
    await ctx.reply("What's your name?")

@survey.step("ask_age")
async def ask_age(ctx):
    await ctx.reply("And your age?")

@survey.finish
async def done(ctx, data):                    # data = {"name": ..., "age": ...}
    await ctx.reply(f"Thanks {data['name']}, registered!")

# Advance the wizard from any handler:
@bot.on(Cmd.start)
async def begin(ctx):
    await survey.enter(ctx)

@bot.on(F.text)
async def advance(ctx):
    await survey.step_forward(ctx, answer=ctx.text)

Graceful Shutdown

Clean exits should be a framework concern, not a per-project copy-paste. bot.run_shutdown() installs signal handlers (SIGINT / SIGTERM), drains the worker pool so in-flight updates finish, and returns — no deadlocks, no lost updates. 

async def main():
    await bot.run_shutdown(timeout=30.0)      # press Ctrl+C — workers drain, then exit

First-Party Plugins

Middleware snippets get copy-pasted between projects forever when nobody ships them officially. SwiftBot's swiftbot.plugins makes common, proven middleware an official, typed registry — the battle-tested four come built in, and the same protocol lets you register your own.

PluginWhat it doesUsage
spam_deflectorDrops users who exceed N messages within a sliding windowbot.use(spam_deflector(threshold=15))
session_limiterPer-user minimum interval between messages (anti-flood)bot.use(session_limiter(min_interval=0.5))
idempotencyDedupe the same update within a window (redeliveries, retries)bot.use(idempotency(window=5.0))
whitelistSilently drop every update not from listed user IDsbot.use(whitelist(user_ids={123}))

The idempotency_guard() transformer (see Transformers) complements the plugin version by making specific outbound calls idempotent for a window — useful for payment confirmations and notification sends.

The F Filter Algebra

Filter syntax should read like plain English. SwiftBot's F preset factory builds fresh, reusable Filter objects with combinators, on top of the framework's existing filter classes — and every preset is a callable, so it plugs straight into any bot.on(...). 

from swiftbot import F

@bot.on(F.text & F.private & ~F.forwarded)
async def a(ctx): ...

@bot.on(F.photo | F.video)
async def media(ctx): ...

@bot.on(F.command("start", "help"))
async def cmd(ctx): ...

@bot.on(F.regex(r"^ping$"))
async def ping(ctx): ...

# Available presets: text, private, group, supergroup, channel, forwarded, reply,
# photo, video, audio, document, voice, sticker, animation, video_note, location, contact, media

State-Carrying Dialogues

A wizard walks a user through steps and accumulates answers; a dialogue goes further — every state carries its own typed data, transitions are declared as a graph, and a per-state timeout can expire a stalled conversation automatically. The dialogue intercepts every update from a user who has an active session, advancing it before any handler runs. 

from swiftbot import Dialogue

survey = bot.dialogue("survey")             # any named storage: Memory / JSON / Redis

# Declared transitions: ask_name may only move to ask_age.
@survey.state("ask_name", next=["ask_age"])
async def ask_name(ctx, prev=None):
    await ctx.reply("What's your name?")
    return Dialogue.next("ask_age", carry=ctx.text)

@survey.state("ask_age", timeout=120.0)     # expires after 2 minutes of silence
async def ask_age(ctx, prev=None):          # prev = the carried name from ask_name
    await ctx.reply(f"Hi {prev}, how old are you?")
    return Dialogue.end                        # end here

@survey.finish
async def finish(ctx, prev):
    await ctx.reply(f"Done! Age: {ctx.text}, name: {prev}")

@survey.on_timeout
async def stalled(ctx, state):
    await ctx.reply("Session expired — send /start again.")

Any update from the user advances the session: transitions are validated against the declared graph (DialogueTransitionError for illegal moves), state data persists through the bot's storage (surviving restarts when using JSONFileStorage or RedisStorage), and the active state is queryable with await survey.current(ctx). Use await survey.exit(ctx) to release a user back to normal routing.

Scoped Middleware

bot.use() installs middleware globally. bot.scope() installs it only where a predicate over the raw update matches — one scope per chat type, one per user, one per business rule. 

# Run only in private chats:
bot.scope(lambda u: u.get("message", {}).get("chat", {}).get("type") == "private") \
   .use(plugins.session_limiter(min_interval=1.0))

# Scopes compose like everything else:
scope = bot.scope(lambda u: u.get("message", {}).get("chat", {}).get("id") in ADMIN_CHATS)
scope.use(admin_gate, audit_logger)
scope.use(bundle.catch(on_plugin_error))       # error boundaries inside scopes too

Outbound Throttling

Telegram's rate limits are per-bot and per-chat — a bot that bursts send_message across a thousand chats gets throttled fast. throttle() is a transformer that holds outgoing calls back with an async-aware token bucket, one queue per chat when configured, and no busy-wait. 

from swiftbot.transformer import throttle

# 20 calls/s globally (bursts of 8), plus at most 4/s per chat.
bot.api.config.use(throttle(max_per_second=20.0, burst=8, per_chat=4.0))

Because it is a transformer, throttling stacks with auto_typing, Recorder, and every other outbound hook — the throttle is the last stage before the network call leaves.

Fluent Reply Builder

Stop hand-building kwarg dicts. Reply(ctx) chains every message option and finishes with .send() — keyboard, caption, parse mode, notification silence, content protection, and raw Bot API parameters all in one readable line. 

from swiftbot import Reply
from swiftbot.button import InlineKeyboard, InlineButton

kb = InlineKeyboard([]).add_row(InlineButton("Confirm", callback_data="ok:1"))

await Reply(ctx) \
    .text("Review the document?") \
    .markup(kb) \
    .protect() \
    .silent() \
    .reply_to(42) \
    .send()

# Media works the same way:
await Reply(ctx).photo(file).caption("Preview").parse_mode("HTML").send()

Fallback & Unknown Commands

Two safety nets cover the updates no handler wants. bot.fallback receives every unmatched update; bot.on_unknown_command receives only /command messages that CommandsMiddleware could not parse against your BotCommands spec. 

@bot.fallback
async def catch_all(ctx):
    await ctx.reply("I didn't catch that — try /help.")

@bot.on_unknown_command
async def unknown(ctx):
    await ctx.reply(f"Unknown command: {ctx.text}. See /help.")

bot.use(CommandsMiddleware(Cmd))               # enables the unknown-command hook

Architecture

An update travels through SwiftBot as a staged chain of responsibility: polling or webhook ingestion → raw dict parsing → worker pool → dispatch routes → pipelines → global middleware / Composer bundles → filter-matched handlers. Handlers send replies through TelegramAPI._request, which passes the call through the transformer stack before hitting the HTTP connection pool. 

Telegram            SwiftBot internals                    HTTP
─────────           ───────────────────────               ────
update ──▶ parse ──▶ WorkerPool (drain on stop)
                  ──▶ bot.route()   ──┐
                  ──▶ pipeline.deps() │  first-match-wins stages
                  ──▶ use() / Composer┘  (boundaries isolate errors)
                  ──▶ filters ──▶ handler(ctx)
                  ──▶ ctx.reply(...) ──▶ transformer stack
                                        (auto_typing, idempotency, Recorder)
                  ──▶ pool.request() ──▶ POST api.telegram.org

Testing lives beside the runtime: TestClient swaps in a FakePool that records every outgoing call and can script responses, while Recorder scripts the transformer layer for API-level tests — together they make it possible to exercise 100% of handler logic without a single network byte.

Upgrade Notes — v1.5 → v1.6

Everything in v1.5 remains intact. v1.6 adds modules and new methods; nothing is removed or renamed. A few notes for upgraders:

  • When a user has an active dialogue, their update is consumed by it before any @bot.on(...) handler runs — if you use dialogues, register step handlers against F.text carefully and use Dialogue.end to release users back to normal routing.

  • Middleware now runs even when no handler matches an update, so that middlewares such as CommandsMiddleware can observe and handle unknown /command messages. Your unmatched updates still reach the fallback handler afterwards as before.

  • A throttle transformer applies to all outgoing API calls once mounted via bot.api.config.use() — place it last so every other transformer sees unthrottled payloads.
